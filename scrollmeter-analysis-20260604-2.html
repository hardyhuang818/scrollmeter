It uses Thunderbolt hardware video bridging (not DisplayLink), so there is no encoding overhead. Browser choice and Chrome GPU setting make no difference.

⚠️ 发现 2：D 组用的是外接鼠标，触控板体验待补测 / Group D Used a Mouse — Trackpad Experience Pending

中文合盖 Clamshell 模式下触控板无法使用，D 组实际测量的是外接鼠标滚轮行为。鼠标滚轮是离散步进事件（15–18/s）；触控板是连续模拟信号（54–111/s）。两者 CV、stuck frames、输入延迟特征完全不同，不可比较。D 组 CV 0.78–0.88 是鼠标的固有步进特性，不代表显示器渲染质量差。

ENIn Clamshell mode the built-in trackpad is unavailable; Group D measured an external mouse scroll wheel. A mouse produces discrete step events (15–18/s); a trackpad produces continuous analog events (54–111/s). Their CV, stuck-frame, and latency profiles are fundamentally incomparable. The CV of 0.78–0.88 in Group D reflects the mouse's inherent step nature, not display rendering quality.

中文同一台 MBP 同一台显示器：内置 HDMI → Hitch 0；DisplayLink → Hitch 10–12 ms/s。HBP Hub 双屏 → Hitch 0。所有硬件视频输出路径均无卡顿，问题唯一出在 DisplayLink 的 USB 软编码链路。

ENSame MBP, same monitor: built-in HDMI → zero hitches; DisplayLink → 10–12 ms/s. HBP Hub dual-screen → zero hitches. All hardware video output paths deliver perfect frames; the bottleneck is exclusively DisplayLink's USB software encoding pipeline.

🟡 发现 4：Safari vs Chrome 差异只在 DisplayLink 下有意义 / Browser Difference Only Matters on DisplayLink

中文硬件视频输出（内置 HDMI、HBP Hub）下 Safari 和 Chrome Hitch 均为 0，浏览器选择无影响。只有 DisplayLink 需要优先选 Safari（2.56 vs 10–12 ms/s）。DisplayLink + Chrome 关闭 GPU 反而更差（12.47 vs 10.09），因为 CPU 渲染与 USB 软编码竞争 CPU 资源。

ENOn hardware video output, both browsers achieve zero hitches — browser is irrelevant. Only on DisplayLink does Safari matter (2.56 vs 10–12 ms/s). Disabling Chrome GPU on DisplayLink makes it worse (12.47 vs 10.09 ms/s) because CPU rasterization competes with USB encoding for CPU time.
