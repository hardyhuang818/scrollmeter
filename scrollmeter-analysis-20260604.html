三、核心发现 / Key Findings

🔴 发现 1：DisplayLink 是卡顿根本原因 / Finding 1: DisplayLink Is the Root Cause of Jank

中文DisplayLink 并非硬件视频输出，而是将画面通过 USB 软件编码传输：CPU/GPU 编码 → USB 传输 → 接收器解码。每一帧都要经过这条链路，受 CPU 负载和 USB 带宽影响，导致实际帧率仅 53.9–59 fps（标称 60Hz 跑不满），Hitch ratio 高达 10–12 ms/s，超过苹果「肉眼可感知」阈值，CV 达 choppy 级别（0.74–0.84）。

ENDisplayLink is not hardware video output. It compresses and transmits the framebuffer over USB: CPU/GPU encode → USB transfer → receiver decode. Every frame goes through this chain, impacted by CPU load and USB bandwidth, resulting in actual frame rates of only 53.9–59 fps, hitch ratios of 10–12 ms/s (exceeding Apple's perceptible threshold), and CV in the "choppy" range (0.74–0.84).

✅ 发现 2：内置 HDMI 接法完全正常 / Finding 2: Built-in HDMI Connection Is Fully Normal

中文同一台 MBP、同一台显示器，换用内置 HDMI 口后，帧率精确 60.0 fps，零卡顿（Hitch ratio = 0），Chrome GPU 开关对结果几乎无影响。说明问题完全出在 DisplayLink 传输层，与显示器本身无关。

ENUsing the same MBP and monitor but switching to the built-in HDMI port, the frame rate is a steady 60.0 fps with zero hitches. Chrome GPU setting makes no meaningful difference. The problem is entirely in the DisplayLink transport layer, not the monitor itself.

🟡 发现 3：Safari 在 DisplayLink 上明显优于 Chrome / Finding 3: Safari Is Significantly Better Than Chrome on DisplayLink

中文同样是 DisplayLink 接法，Safari 的 Hitch ratio 仅 2.56 ms/s（流畅），而 Chrome 高达 10–12 ms/s（卡顿）。Safari 使用 Metal / Core Animation 直接与 macOS 显示管线整合，对 DisplayLink 引入的额外延迟有更好的容忍；Chrome 采用自有 Chromium Viz 合成器，与 DisplayLink 配合更差。

ENOn the same DisplayLink setup, Safari's hitch ratio is only 2.56 ms/s (smooth), while Chrome reaches 10–12 ms/s (jank). Safari uses Metal / Core Animation deeply integrated with the macOS display pipeline, tolerating DisplayLink's added latency better. Chrome's Chromium Viz compositor operates independently and conflicts more severely with DisplayLink overhead.

🟡 发现 4：DisplayLink 下关闭 Chrome GPU 加速反而更差 / Finding 4: Disabling Chrome GPU on DisplayLink Makes Things Worse

中文关闭 GPU 加速后 Hitch ratio 从 10.09 升至 12.47 ms/s。原因：软件渲染（CPU rasterization）与 DisplayLink 的 USB 编码同时抢占 CPU 资源，两者竞争加剧。在 DisplayLink 环境下，Chrome GPU 加速应保持开启。

ENDisabling GPU acceleration raises the hitch ratio from 10.09 to 12.47 ms/s. CPU rasterization and DisplayLink's USB encoding compete for the same CPU resources, worsening contention. On a DisplayLink setup, Chrome GPU acceleration should remain enabled.
